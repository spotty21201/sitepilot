# Independent SitePilot Audit

**Outcome:** SitePilot has a credible Release 1 foundation — especially its deterministic geometry, compliance, evidence classification, and scenario model — but it is not yet a complete professional spatial-planning product. The current production 3D experience is a custom raw Three.js editor façade, not a mounted Pascal Editor integration. The geographic workflow is still largely synthetic: new cases use a fixed Jakarta coordinate and rectangular boundary regardless of the entered address. The recommended path is an incremental hybrid: retain and strengthen the canonical domain, build a purpose-specific spatial editor behind an adapter boundary, and add a separate map/parcel/provenance layer.

No production code, configuration, dependency, data, deployment, or commit was changed. Only the permitted audit plan file was written: `/home/spotty/.claude/plans/ancient-knitting-salamander.md`.

## 1. Executive assessment

### Overall assessment

**VERIFIED:** SitePilot is a functional decision-room prototype with:

- a typed project aggregate;
- evidence classifications;
- contradictions and unknowns;
- deterministic massing metrics;
- deterministic compliance evaluation;
- multiple scenarios;
- local persistence;
- numeric mass editing;
- browser-visible DAE export;
- a decision summary and investigation queue.

**PARTIAL:** It is not yet a coherent end-to-end professional product because the crucial transitions between geographic evidence, authoritative parcel geometry, scenario editing, persistence, and export are incomplete or disconnected.

The strongest current architecture is:

```
Scenario mass state
    ↓
Deterministic geometry engine
    ↓
Metrics + collisions + setbacks + compliance
    ↓
Decision-room panels + local persistence + DAE generation
```

The weakest current architecture is:

```
Address entered by user
    ↓
Fixed Jakarta coordinate and polygon
    ↓
Rectangle derived from area/frontage
    ↓
Illustrative 3D massing
```

That is not yet a real site-ingestion workflow.

### Principal findings

1. **VERIFIED — Canonical geometry is a real foundation.**
   `src/lib/geometry/engine.ts` calculates parcel bounds, mass unions, GFA, FAR, coverage, open space, height, collision, setbacks, out-of-bounds footprint, and compliance.
2. **VERIFIED — The production 3D path is not Pascal.**
   `src/app/page.tsx:5,539-543` mounts DevelopmentWorkspace.
   `src/features/development-3d/DevelopmentWorkspace.tsx:11,328-346` mounts ViewportCanvas.
   `src/features/development-3d/ViewportCanvas.tsx:128-478` manually creates the Three.js scene and renderer.
3. **VERIFIED — Pascal code exists but is disconnected from the production path.**
   `PascalEditorView.tsx` dynamically imports `pascal-app/editor`, but no production import reaches it.
   `adapter.ts` and `pascal-plugin.ts` define translation and diagnostic metadata; they do not prove editor runtime integration.
4. **VERIFIED — New cases are geographically synthetic.**
   `createCase()` writes a fixed Jakarta center and fixed polygon in `src/lib/storage/case-repository.ts:617-690`, regardless of the address supplied by the user.
5. **VERIFIED — The current editor is not SketchUp-like in the interaction sense.**
   It supports selection, numeric dimensions, custom resizing handles, floors, duplicate/delete, and local undo/redo. It does not implement predictable orbit, pan, zoom, move, rotate, robust snapping, section planes, true dimensions, or floor isolation.
6. **VERIFIED — Export is not yet a server-authoritative canonical pipeline.**
   The client generates a DAE blob from active state. The GET API can fall back to Golden Project or synthetic geometry. The POST API accepts client-supplied geometry.
7. **VERIFIED — The export acceptance contract is inconsistent.**
   The actual runtime DAE contains `Z_UP`. The browser acceptance script checks for `Y_UP`.
8. **VERIFIED — Test discovery is contaminated by untracked worktrees.**
   The clean source suite passes when `.claude/worktrees/**` is excluded: 12 files and 61 tests. The declared `npm test` command discovers nested worktrees and fails on duplicated stale tests.

### Product conclusion

**RECOMMENDATION:** Do not rewrite the whole application. Preserve:

- the canonical geometry engine;
- the typed evidence/scenario model;
- the compliance evaluator;
- the decision-room concept;
- the local persistence abstraction as a temporary adapter.

Refactor the system around:

- a canonical command/revision model;
- a real polygon and coordinate-reference workflow;
- a SpatialEditorAdapter;
- a dedicated map/context adapter;
- a server-authoritative export pipeline;
- an explicit evidence-quality model.

## 2. Reconstructed SitePilot intention and product goals

### What problem SitePilot is intended to solve

**VERIFIED — PRD intention:** SitePilot is intended to be the early development decision layer connecting:

- fragmented property evidence;
- mapping and site context;
- verified facts and claims;
- planning and physical constraints;
- development metrics;
- lightweight 3D scenarios;
- investment and decision support.

The PRD describes the transformation as:

> “Someone sent me a possible site.”

to:

> “I understand the opportunity, the risks, approximately what can be developed, what remains uncertain, and what I should do next.”

Source: `SitePilot — Product Requirements Document v1.0.md:11-54`.

The product is explicitly positioned between several categories:

- not quite GIS;
- not quite SketchUp;
- not quite a feasibility spreadsheet;
- not quite document AI;
- not quite an investment dashboard;
- not quite an architectural design application.

Source: `SitePilot — Product Requirements Document v1.0.md:81-101`.

That distinction matters. The product does not need to become a general CAD application to succeed. It needs to become a trustworthy early-stage spatial decision system.

### Users and decisions

**VERIFIED:** The primary user is a senior development professional evaluating land or property:

- development adviser;
- architect;
- master planner;
- urban planner;
- developer;
- development manager;
- property consultant.

Secondary users include:

- investors and family offices;
- acquisition teams;
- asset managers;
- planning consultants;
- development companies;
- multidisciplinary design teams.

Source: `SitePilot — Product Requirements Document v1.0.md:113-143`.

Their decisions differ:

| User | Primary decision |
|---|---|
| Architect | What massing strategies could physically fit, and what constraints should guide early design? |
| Planner | Which controls are authoritative, which are assumed, and what conflicts require investigation? |
| Developer | Does the site justify further acquisition, design, survey, or consultant spend? |
| Investor / analyst | What is the opportunity, downside, uncertainty, and scenario sensitivity? |
| Multidisciplinary team | Can everyone discuss the same evidence, geometry, assumptions, and revision? |

### Core product questions

**VERIFIED:** The PRD says SitePilot must continuously answer:

1. What do we know?
2. What do we not know?
3. Why does it matter?
4. What could be developed?
5. What should happen next?

Source: `SitePilot — Product Requirements Document v1.0.md:186-218`.

This is a stronger product spine than “AI plus 3D.” Every feature should support one or more of those questions.

### Product promises already implemented

**VERIFIED:**

- Project and opportunity creation.
- Evidence classification types.
- Contradiction model.
- Deterministic development metrics.
- Setback and collision checks.
- Scenario creation and switching.
- Scenario duplication.
- Scenario comparison modal.
- Executive summary.
- Investigation actions.
- Numeric mass properties.
- Local persistence.
- Client DAE download.
- Server-side deterministic assessment precomputation.

### Promises that are partial, simulated, hard-coded, disconnected, or absent

**PARTIAL:** New cases can be created, but the site location is not truly resolved geographically.

**PARTIAL:** Evidence extraction exists as an API, but new-case creation does not connect the user-facing intake to that extraction flow.

**VERIFIED:** The current 2D view is a rectangular SVG study plan, not a geographic cadastral map.

**VERIFIED:** `maplibre-gl` is installed, but no production import was found.

**VERIFIED:** The current scene is manually generated from rectangular bounds and block masses.

**MISSING:** Address search, parcel retrieval, boundary drawing, boundary reconciliation, CRS selection, survey metadata, coordinate transformation, real terrain, surrounding context, and provider attribution.

**MISSING:** Server-backed versioned case persistence and collaboration.

**PARTIAL:** Export produces a structured DAE, but it is not yet a verified, server-authoritative, georeferenced round trip.

### What SitePilot must become

**RECOMMENDATION:** SitePilot should become a spatial evidence and scenario decision workspace with four explicit layers:

1. **Evidence layer** — what sources say and how trustworthy they are.
2. **Geographic layer** — where the site is and what geometry is authoritative.
3. **Canonical planning layer** — what the current working model calculates.
4. **Presentation/editor layer** — how the user views and edits that model.

The editor must remain subordinate to the canonical planning model.

## 3. Intended end-to-end professional workflow

The PRD describes six broad activities:

**Capture → Understand → Investigate → Explore → Decide → Advance**

They are not a mandatory wizard. Professionals must be able to move between them freely.

### 1. Capture

The user may start with:

- an address;
- a map location;
- a WhatsApp message;
- a broker brochure;
- a certificate photograph;
- rough coordinates;
- site photographs;
- an investment idea;
- an approximate boundary.

The product should allow:

- project name;
- location or pin;
- development objective;
- optional asking price;
- optional claimed area;
- optional evidence;
- optional rough boundary.

### 2. Understand

The system should present:

- approximate location;
- claimed or measured site area;
- objective;
- evidence received;
- initial confidence;
- major unknowns;
- initial planning assumptions.

The user must be able to correct a working value without deleting the original evidence.

### 3. Investigate

The system should maintain:

- source inventory;
- extraction status;
- findings;
- citations;
- evidence classification;
- contradictions;
- confidence;
- issues;
- investigation actions.

When evidence conflicts, the user should see:

- the competing values;
- the sources;
- the reason for the conflict;
- impact on metrics/scenarios;
- recommended verification;
- the selected working value;
- the status of that working value.

### 4. Spatial investigation

The user should be able to inspect:

- basemap;
- satellite imagery;
- parcel candidates;
- adopted boundary;
- roads;
- access;
- planning overlays;
- setbacks;
- easements;
- water;
- slope;
- no-build areas;
- opportunities;
- annotations;
- measurements.

### 5. Explore development

The user should be able to:

- generate a scenario;
- duplicate a scenario;
- edit a footprint;
- move a mass;
- rotate a mass;
- resize a mass;
- set floor count;
- set floor-to-floor height;
- change program;
- inspect constraints;
- compare alternatives.

Every edit must update:

- canonical geometry;
- metrics;
- compliance;
- warnings;
- scenario status;
- badges;
- persistence;
- reports;
- exports.

### 6. Decide and advance

The decision view should show:

- opportunity;
- material risks;
- critical unknowns;
- development potential;
- preferred scenario;
- scenario sensitivity;
- recommended next move;
- unresolved evidence;
- owner/status of investigation actions.

The result should be transferable to:

- survey;
- planning consultant;
- investor discussion;
- acquisition negotiation;
- SketchUp;
- financial feasibility;
- master planning;
- later architectural design.

## 7. 3D interaction and visual-design critique

### Current interaction architecture

#### Selection

**VERIFIED:** Selection uses raw Three.js raycasting against mass meshes:

`src/features/development-3d/ViewportCanvas.tsx:500-558`.

It is object-level selection only.

**MISSING:**

- hover/preselection;
- face selection;
- edge selection;
- selection hierarchy;
- keyboard selection;
- selection history;
- explicit selected-object provenance.

`onHoverMass` exists in the props interface but is not wired into a real hover system.

#### Direct manipulation

**VERIFIED:** Custom arrow geometry is generated locally in `PascalTransformHandles.tsx`. The handles are visually Pascal-inspired but not Pascal runtime handles.

The drag logic:

- reads screen-space pointer movement;
- uses a fixed 0.15 meters-per-pixel sensitivity;
- rounds to 0.5 m;
- directly updates mass dimensions;
- updates GFA during drag.

Reference: `ViewportCanvas.tsx:560-645`.

This is not geometry-aware drag manipulation. It will behave differently depending on:

- camera distance;
- projection;
- viewport size;
- screen density;
- pointer movement;
- perspective distortion.

#### Camera

**VERIFIED:** Perspective and orthographic cameras exist, with TOP/SOUTH/NORTH/EAST/WEST/ISO/RESET presets.

**MISSING:**

- orbit;
- pan;
- zoom;
- zoom-to-selection;
- fit-to-site;
- camera target preservation;
- camera navigation parity across input devices.

Auto-orbit is an animation feature, not a navigation model.

#### Tools

**VERIFIED:** `ManipulationTool` declares:

```ts
'SELECT' | 'MOVE' | 'RESIZE' | 'HEIGHT'
```

Reference: `src/features/development-3d/types.ts:8`.

**VERIFIED:** The production viewport does not implement separate move, resize, and height tool behavior based on that state. Resize/height handles are always based on selection. The toolbar's tool state is therefore partly façade.

#### Numeric input

**VERIFIED:** `MassPropertiesPanel` supports:

- width;
- length;
- floors;
- floor-to-floor height;
- X;
- Z;
- program.

Reference: `src/features/development-3d/MassPropertiesPanel.tsx:209-297`.

This is one of the most valuable current features and should be retained.

#### Snapping

**PARTIAL:** Only direct resize uses 0.5 m screen-delta rounding.

**MISSING:**

- parcel vertices;
- parcel edges;
- setback boundaries;
- buildable-envelope edges;
- mass edges;
- vertices;
- axes;
- configurable grid;
- visible snap target;
- angular snapping;
- snap priority rules.

#### Dimensions and measurements

**VERIFIED:** The toolbar exposes a dimension toggle and drag HUD.

**VERIFIED:** No actual dimension overlay consumes `showDimensions` in `ViewportCanvas`.

This is a concrete source defect: the interface promises dimensions but the implementation does not render general dimensions.

#### Sections and floors

**VERIFIED:** A level selector is rendered.

**MISSING:** It does not actually isolate or clip geometry by floor. It mostly changes selection state and displays floor metadata.

### SketchUp-like target interaction model

**RECOMMENDATION:** "SketchUp-like" should mean:

- predictable camera behavior;
- direct object manipulation;
- visible axes and snap intent;
- exact numeric entry;
- reversible edits;
- constraint-aware previews;
- clear spatial hierarchy.

It should not mean arbitrary CAD parity.

Required tools:

1. Select.
2. Move.
3. Rotate.
4. Resize footprint.
5. Height/floors.
6. Duplicate.
7. Delete.
8. Measure.
9. Section.
10. Isolate floor.
11. Compare.

Every tool must produce a typed canonical command.

## 8. Geographic and parcel-ingestion assessment

### Current status

**MISSING:** The current product does not yet provide a real geographic workflow.

The type model includes:

```ts
coordinateSystem: 'WGS84' | 'EPSG:3857'
```

and GeoJSON types, but the actual case creation path uses:

- fixed Jakarta center;
- fixed Jakarta polygon;
- fixed WGS84 label;
- rectangular local modelling dimensions.

References:

- `src/types/index.ts:40-69`
- `src/lib/storage/case-repository.ts:617-690`

### Recommended ingestion sequence

1. Search for an address/place.
2. Confirm the map location.
3. Retrieve a parcel candidate from an authoritative provider where available.
4. Let the user accept, correct, draw, or trace a boundary.
5. Allow exact coordinates, bearings, distances, and vertices.
6. Import GeoJSON/KML/KMZ first.
7. Import zipped Shapefile with `.prj`.
8. Treat DXF as a controlled spike.
9. Treat DWG as a conversion/service decision.
10. Reconcile candidate boundaries.
11. Store provider, source, date, CRS, units, accuracy, authority, and user edits.
12. Transform to a local metric project frame.
13. Preserve source and transformed geometry.
14. Create scenarios against a specific boundary version.
15. Mark scenario impact if the adopted boundary changes.

### Provider separation

**VERIFIED from official Google documentation:** Google Photorealistic 3D Tiles provides textured 3D mesh context for visualization. It is accessed through a compatible 3D Tiles renderer, with CesiumJS documented as an example. The page describes visualization, not parcel editing. Attribution is required. Google requires a project, billing, Map Tiles API enablement, API key, and compliance with Maps terms and policies.

Sources:

- Google Photorealistic 3D Tiles: <https://developers.google.com/maps/documentation/tile/3d-tiles>
- Google Map Tiles policies: <https://developers.google.com/maps/documentation/tile/policies>
- Google Maps Platform terms: <https://cloud.google.com/maps-platform/terms/>

**RECOMMENDATION:** Keep these provider roles separate:

| Responsibility | Possible provider |
|---|---|
| Address/place search | Google, Mapbox, another geocoder |
| Basemap/vector tiles | MapLibre-compatible provider, Mapbox, Google |
| Satellite/imagery | Separate imagery provider |
| Parcel/cadastral boundary | Government/municipal/private cadastral source |
| Terrain/elevation | DEM/terrain provider |
| Photorealistic context | Google Photorealistic 3D Tiles, Cesium ion, other licensed source |
| Planning/zoning | Government planning data or uploaded evidence |
| Survey/CAD | User source documents and imported geometry |

### CRS and local coordinates

**RECOMMENDATION:** Maintain three representations:

1. Original source CRS and units.
2. Normalized geographic coordinates.
3. Local engineering coordinates for canonical editing.

The local frame should contain:

- origin;
- orientation;
- local CRS/ENU transform;
- vertical datum;
- units;
- precision;
- source CRS;
- transform operation;
- source centroid.

Do not use Web Mercator as the precision modelling CRS. It is useful for visualization but not ideal as the authoritative local engineering frame.

### Evidence-quality communication

Use explicit labels:

- Authoritative cadastral
- Surveyed
- Imported source
- User-corrected
- Indicative trace
- Illustrative study
- Assumption
- Unknown

A visually precise basemap must not make an uncertain parcel appear authoritative.

- purpose-built Three.js/R3F editor for SitePilot-owned parcel/envelope/massing;
- optional Pascal/That Open/APS integrations for isolated viewing/spikes only.

### Runner-up

Purpose-built Three.js/R3F editor with a separate map adapter and no third-party editor framework.

### Rejections

- **Pascal as automatic replacement:** no production mount proof; package is not a direct root dependency; current editor path is disconnected.
- **Cesium alone:** excellent geographic visualization, not a canonical massing editor.
- **MapLibre/deck.gl alone:** map/rendering infrastructure, not a solid editor.
- **That Open alone:** strong BIM/AEC viewing capabilities, but not sufficient as a general planning massing editor.
- **APS Viewer as core:** external model viewing and vendor/cloud dependence do not align with SitePilot's canonical geometry ownership.
